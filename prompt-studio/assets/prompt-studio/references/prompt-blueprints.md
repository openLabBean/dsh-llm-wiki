# 提示词蓝图（八段式 · 三格式 · 句库 · 反模式）

> 本文件是 `prompt-optimizer` 技能的写作蓝图。产出提示词时**照此拼装**，不要自由发挥结构。
> 所有"规范"类事实都来自 `wiki/templates/word-文档写作模板.md` 与 `ppt-演示文稿写作模板.md`；本文件只是把规范翻译成「提示词里该怎么写」。

---

## 一、八段式总表

| # | 段落 | 必须回答的问题 | 依据来源 |
|---|---|---|---|
| 1 | **角色** | 你以什么身份、什么专业口径来做这件事？ | 场景 + 产品域 |
| 2 | **任务** | 产出一份什么文档？核心要证明/讲清哪一句？ | 用户需求 |
| 3 | **知识库依据** | 用哪些已核实的事实？路径 + 结论 + 置信度 | `kb.mjs search` + 精读页面 |
| 4 | **输出规格** | 格式、母版、规范页、骨架、篇幅、命名 | `spec` 输出 + 规范页 |
| 5 | **受众与口径** | 给谁看？内部/外发/公开？哪些话不能说？ | `templates/README.md` §3.1 |
| 6 | **写作与证据规范** | 结论先行？数字出处？图表编号？术语？ | 规范页 §四/§五 |
| 7 | **验收清单** | 交付前逐项自检什么？ | 规范页自检清单（Word 10 项 / PPT 11 项） |
| 8 | **未决问题与交付方式** | 哪些是假设？先交什么、后交什么？ | 缺口判断 |

**判断标准**：把这段提示词交给一个完全不了解背景的 AI，它能否**不追问、不编造**地做出 80 分的初稿？能 → 合格。

## 二、通用模板（按格式填空）

```text
# 角色
你是浩鲸科技 BI 产品团队的产品设计/文档专家，熟悉 WhaleBI（BI Report 可视化报表）与 ChatBI（智能问数）的产品体系、术语与对外口径。

# 任务
产出一份《<文档标题>》（<Word 文档 / PPT 演示文稿 / Markdown 内容源>，<场景>）。
核心目标：<一句话——这份文档要让读者相信/知道/决定什么>。
不做：<范围外内容，避免跑题>。

# 知识库依据（已核实，不得替换为自己编造的内容）
1. `wiki/<路径>` — <可直接引用的结论或数字>（<置信度>，<日期>）。
2. `wiki/<路径>` — <……>。
3. 用户提供：<客户名/版本号/会议结论>（来源：用户输入）。
事实规则：
- 只能使用以上依据 + 用户输入；缺依据的结论标 【待验证】 并列入"待确认"。
- 数字必须带出处与日期；竞品信息只用官方公开材料。
- 不引用未公开的客户信息与合同信息。

# 输出规格
- 格式：<.docx | .pptx>；命名：`YYYYMMDD-<产品>-<主题>-<版本>.<ext>`（未定稿用 V0.x）。
- 母版：`<绝对路径>`（只读，另存产出，不在母版上改内容）。
- 规范页：`<绝对路径>`（场景骨架见 §<x>，自检清单见 §<y>，已知缺口见 §<z>）。
- 结构骨架：<按场景粘贴骨架，见第四节>。
- 篇幅：<8–20 页 / 15–20 页 / 6–15 页>；<一句话说明超限怎么处理>。
- 图表：<图 3-1 / 表 3-2 编号 + 标题 + 单位 + 口径/来源脚注>。

# 受众与口径
- 受众：<内部研发 / 管理层 / 客户高层 / 一线运维>；阅读场景：<评审会 / 汇报 / 培训 / 存档>。
- 口径：`内部` | `外发` | `公开`。
  - 外发：隐去 Hermes 等底层开源框架名，统一称"自研 Agent 引擎"；不出现源码路径、内部表名、未公开客户信息。
  - 铁律一：隐去 ≠ 改称自研的不实能力（不得替换为不真实归属）。
  - 铁律二：不得删除应有的第三方引用（引用竞品/论文须保留出处）。
- 语气：主动语态、祈使句；不用"可能/大概"等模糊限定，无法确定就用置信度标注代替。

# 写作与证据规范
- 每节先一句结论，再论据/证据，最后补充；禁止"只有标题没有内容"的空节。
- Word：标题最多三级；图表按章编号；术语首次给全称，附录给术语表。
- PPT：每页标题必须是结论句；一页一个结论，正文 ≤6 行、每行 ≤2 分句；图 > 表 > 字；用母版版式，不手工堆文本框。
- 结论标注：`【已验证】`（有实现/文档佐证）/`【推断】`（由素材推理）/`【待验证】`（单一来源未交叉确认）。

# 验收清单（交付前逐项自查，缺项要说明原因）
- [ ] <从规范页自检清单逐条粘贴>

# 未决问题（写作中如无法从依据得出结论，列在这里，不要猜）
1. <问题> —— 影响：<哪一节>；最省事的确认方式：<一句话>。

# 交付方式
1. 先在 `<工作区路径>` 写 Markdown 内容源；2. 确认章节与口径后，套母版导出成品；
3. 汇报：完成项 / 未决项 / 口径说明 / 与上一版差异（如有）。
```

## 三、三格式变体（只写差异，通用段照抄上面）

### 3.1 Word 文档（`.docx`）

| 段 | 变化 |
|---|---|
| 角色 | 加"擅长结构化需求方案/规划/复盘写作" |
| 输出规格 | 母版 `wiki/templates/Typora-Word2.docx`；规范页 `word-文档写作模板.md`；骨架用其**通用结构骨架** + **场景骨架**（§三）；篇幅方案类 8–20 页 |
| 写作规范 | 标题最多三级；每节结论先行；图表按章编号；强调只用加粗 |
| 验收清单 | Word 10 项（封面与信息表含口径、修订记录、标题层级与目录、数字出处、置信度、口径合规、图表、遗留决策点、术语、排版四项、命名）——**以规范页 §六 原文为准** |
| 特有提醒 | ⚠️ 母版未定义 Heading 1–9：导出后必须检查导航窗格层级与目录能否更新；中文字体需确认 |

### 3.2 PPT 演示文稿（`.pptx`）

| 段 | 变化 |
|---|---|
| 角色 | 加"擅长把复杂结论压缩成一页一个观点的汇报材料" |
| 输出规格 | 母版 `wiki/templates/浩鲸科技_20周年_ppt中文模板_白.potx`；规范页 `ppt-演示文稿写作模板.md`；页序按**场景页序对照**（§六）；20 分钟 ≈ 15–20 页 |
| 写作规范 | **每页标题写结论句**；一页一个观点；正文 ≤6 行；版式按正文占位符数量选（×1 观点/结论，×2 对比，×3 三要点）；主色 ≤2 个（accent4 #0082FF / accent3 #00B4FF），同指标跨页同色；图表有单位/口径/来源/日期 |
| 验收清单 | PPT 11 项（结论句标题、一页一论点、母版版式与页码、主题字体、配色、图表信息、涨跌配色标注、口径合规、总结页含负责方与时间、页数匹配、命名）——**以规范页 §八 原文为准** |
| 特有提醒 | 7 个版式未按用途命名，只能按正文占位符数量判断；不放未公开客户名 |

### 3.3 Markdown 内容源（`.md`）

| 段 | 变化 |
|---|---|
| 用途 | wiki 只存内容源，成品二进制不入库；适合研究稿、设计稿、竞品分析底稿 |
| 输出规格 | 骨架复用 Word/PPT 的章节骨架；存放 `wiki/deliverables/<类型>/YYYYMMDD-<产品>-<主题>.md`；带 frontmatter（title/type/domain/tags/source_count/created/last_updated/status） |
| 写作规范 | 同 Word：先结论后论据、数字带出处、置信度标注、术语统一；结尾"来源"小节列 raw/ 或 wiki 路径 |
| 验收清单 | frontmatter 完整、结论可回溯到来源、无孤岛（至少链接 2 个已有页面） |

## 四、场景 → 骨架映射（写"输出规格"时直接粘贴）

### Word

| 场景 | 第三节展开结构 |
|---|---|
| 需求方案设计 | 需求描述 → 用户场景与故事 → 功能设计（交互/状态）→ 数据与技术设计 → 验收标准 → 遗留决策点 |
| 年度规划 | 年度目标 → 主题/战役拆解 → 季度节奏 → 资源与依赖 → 风险 |
| 季度规划 | 上季度回顾 → 本季度目标 → 需求/版本清单（版本轴）→ 里程碑 → 依赖与风险 |
| 月度迭代 | 本月范围 → 需求清单与状态 → 发布计划 → 遗留问题（状态：待开发/开发中/待验证/已发布/已延期） |
| 竞品研究 | 定位 → 功能架构 → 技术架构 → 能力对照 → 对我方启示 → 局限与风险 |
| 发布说明 | 版本概览 → 新增/优化/修复 → 影响与兼容 → 升级与回滚 → 已知问题 |
| 验证复盘 | 目标与验收标准 → 实测结果 → 偏差与根因 → 结论 → 后续动作 |
| 会议纪要 | 议题 → 结论 → 待办（负责人/截止）→ 未决事项 |

### PPT 页序

| 场景 | 页序（约 15–20 页） |
|---|---|
| 季度/年度规划汇报 | 封面 → 目录 → 上期回顾(1–2) → 本期目标(1) → 重点战役(3–4) → 版本/里程碑路线图(1–2) → 资源与依赖(1) → 风险(1) → 总结与下一步(1) → 附录 |
| 需求方案评审 | 封面 → 目录 → 问题与证据(1–2) → 目标与范围(1) → 方案总览(1) → 关键流程(2–3) → 交互/原型(2) → 验收标准(1) → 待决策(1) → 附录 |
| 竞品分析汇报 | 封面 → 目录 → 市场与定位(1) → 竞品架构(2) → 能力对照矩阵(1–2) → 我方定位与差距(1–2) → 启示与建议(1) → 附录（来源） |
| 产品发布/对外赋能 | 封面 → 目录 → 客户痛点(1–2) → 能力总览(1) → 场景演示(3–4) → 价值与案例(2) → 落地路径(1) → 总结(1) |

## 五、句库（按段落挑用，保持短句）

**角色**
- 你是浩鲸科技 BI 产品团队的产品设计专家，负责把业界研究与产品设计落成可评审的文档。
- 你以「内部评审」口径写作，读者是研发与产品负责人，可以直接出现框架名与实现细节。
- 你以「对外汇报」口径写作，任何底层框架名都要隐去，统一表述为"自研 Agent 引擎"。

**任务**
- 核心目标：用 <3 条依据> 说服 <受众> 接受 <结论/方案>。
- 只回答一个问题：<一句话命题>；其余内容一律削掉。
- 不写：<范围外>；如果读者可能追问，放到附录。

**依据**
- 以下结论已核实，可直接引用；未列出的结论不得自行补充。
- `wiki/xxx`（更新 YYYY-MM-DD，【已验证】）：<结论>。
- 竞品数据只引用官方公开材料，转引自述数据标【待验证】并保留出处 URL。

**输出规格**
- 按《word-文档写作模板》§三「场景骨架」中的「<场景>」组织第三节，其余章节用通用骨架。
- 套用母版 `<路径>`，只读；输出文件另存为 `YYYYMMDD-<产品>-<主题>-V0.9.docx`。
- PPT 页序按规范页 §六「<场景>」，页数控制在 <N> 页以内；每页标题写结论句。

**口径**
- 口径 `外发`：隐去 Hermes 等底层开源框架名；不得因脱敏改称自研的不实能力；不得删除第三方引用。
- 涉及客户名、合同、未公开路线图的内容一律不写，改为能力描述。
- 拿不准的表述标【待验证】，不要用"大概/可能"糊过去。

**验收**
- 交付前逐项核对规范页自检清单；任何未达标项必须在汇报里说明原因与补救计划。
- 每个数字都能回溯到 `wiki/` 页面或 raw 素材；每个竞品结论都有出处。

**未决**
- 以下问题若无法从依据中确定，写进"未决问题"并在交付时提醒，不要自行假设：
- 待确认：<问题>（影响 <章节>；确认方式：<一句话>）。

## 六、反模式清单（优化前后的典型动作）

| # | 烂提示词特征 | 问题 | 修正动作 |
|---|---|---|---|
| 1 | "帮我写个 PPT，关于 ChatBI" | 无场景、无受众、无结论 | 补场景（汇报/评审）+ 受众 + 一句核心结论 |
| 2 | "参考知识库写就行" | 指令不可执行，模型只能编 | 换成具体 `wiki/路径` + 结论 |
| 3 | "要专业、要有深度" | 形容词无法验收 | 换成验收清单（标题结论句、数字出处…） |
| 4 | "内容越多越好" | 篇幅失控 | 给页数/字数区间 + 超限处理规则 |
| 5 | 没提口径 | 外发材料泄内部实现 | 显式写 `内部/外发` + 脱敏规则 |
| 6 | "把网上资料整理一下" | 来源不可控 | 限定知识库 + 官方公开材料 |
| 7 | 模板要求凭记忆写 | 母版规格写错 | 先跑 `spec`，路径与规格照抄 |
| 8 | 只给主题不给骨架 | 结构随机 | 粘场景骨架（三四节表格） |
| 9 | 忽略已知缺口 | 导出后目录/标题出错 | 写入"已知缺口"提醒（Heading 样式缺失等） |
| 10 | 优化成 3000 字长文 | 信息密度低 | 控制在 600–1500 字，删形容词与空话 |

## 七、交付回复模板

```text
## 优化点摘要
1. 补全了什么（场景/受众/篇幅）
2. 注入了哪些依据（wiki 页面 + 结论）
3. 锁定了什么规格（格式/母版/骨架/命名）
4. 明确了什么口径（内部/外发 + 红线）
5. 加了什么验收标准
6. 还缺什么（待确认）

## 可直接复制的提示词
<八段式提示词>

## 依据与置信度
- wiki/… — 支撑"……"（【已验证】/【推断】/【待验证】）
- 建议先摄入：…

## 下一步
- 说"就按这个做"→ 我直接生成文档
- 说"再短一点/换成 PPT/更专业"→ 我只改对应段落
```
