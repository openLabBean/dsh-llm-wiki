# 提示词增强器（DataPilot 知识库增强）

> **输入**是「粗糙需求」；**输出**是「可直接执行的专业提示词」：带知识库依据、带输出规格、带口径红线、带验收清单。
> **默认只交付提示词，不直接写文档**；用户明确说"直接做/生成文档/按这个写"时才继续执行（见第 6 步）。

> **与侧边栏面板的分工**：DSH 侧边栏里的「提示词增强器」面板会**检索知识库并调用大模型**生成提示词（角色 / 任务 / 原始需求 / 知识库依据 / 输出规格，原型新 demo 附技术架构），不再输出验收清单、未决问题、交付方式或写作规范章节。
> 本技能负责**深度改写**：用户从面板点「复制给 AI 深度优化」后，消息以 `/prompt-optimizer` 开头，此时你要做的是——检索并精读知识库、核对依据、把口语化需求改写成更准确的八段式提示词，并给出「优化点摘要 / 依据与置信度 / 未决问题」。不要重复面板已给出的模板路径，除非需要纠正。


## 〇、先锁定交付物

- 交付物 = 一段**可以直接复制粘贴、脱离本次对话也能执行**的提示词（放在代码块里）。
- 不是交付文档本身，不是把 wiki 内容抄一遍，也不是替用户做业务决策。
- 优化 ≠ 扩写：宁可短而准，不堆形容词、不写"请参考知识库"这类空洞指令。

## 一、工作流（按序执行，不要跳步）

### 第 0 步：抽取槽位（内部完成，不要输出长表格）

| 槽位 | 处理方式 |
|---|---|
| **文档类型** | Word(.docx) / PPT(.pptx) / Markdown / 交互原型 / 两者都要；判断不了先跑 `spec auto` |
| **场景** | 需求方案 / 年度规划 / 季度规划 / 月度迭代 / 竞品研究 / 发布说明 / 验证复盘 / 会议纪要 / 包装材料 / 演进研究 |
| **产品域** | RPT 报表 / AGT 智能问数 / PLT 智能体平台 / RAG 检索 / ONT 本体 / MIXED 跨域 |
| **主题** | 一句话核心命题（"要证明/要讲清什么"，不是"写个 PPT"） |
| **受众** | 内部研发 / 管理层 / 客户高层 / 一线运维；受众决定详略与口径 |
| **口径** | 内部 / 外发 / 公开。**涉及客户、市场、对外场合一律默认 `外发` 并提示确认** |
| **篇幅与时限** | 页数/字数/交付时间；缺失时用规范页默认值（Word 8–20 页，PPT 15–20 页） |
| **已有素材** | 链接、文件、会议记录、版本号；没有则列入待确认 |

- 关键槽位缺失 ≥3 个：**一次问完最多 3 个问题**（只问"答错会返工"的），其余写"假设 + 待确认"。
- 用户已给出硬约束（版本号、客户名、日期、篇幅、必须包含的章节）：**原样保留，不得改写**。

### 第 1 步：知识库检索（强制，先于任何写作）

用运行时配置里的绝对路径替换下面两个占位：`<检索脚本>`、`<知识库>`。

```bash
node "<检索脚本>" --kb "<知识库>" info
node "<检索脚本>" --kb "<知识库>" search "<关键词>" --top 12
node "<检索脚本>" --kb "<知识库>" spec <docx|pptx|md|auto>
```

- 关键词 = **产品名 + 机制名 + 竞品名 + 场景词**，2–6 个，不要整句。例：`search "ChatBI 自动化任务 定时触发 竞品"`。
- 命中 <3 条或明显跑偏：换同义词再搜一次（最多 2 轮），如「智能问数 / 自然语言查数 / NL2SQL」「报表 / 看板 / BI Report」。
- `spec` 输出的是**规范摘要**，直接用于提示词的"输出规格"段。若摘要里写了"硬性细节以规范页为准"，第 2 步必须读规范页对应小节。

### 第 2 步：精读命中页面（3–6 页，按需）

```bash
node "<检索脚本>" --kb "<知识库>" outline <页面相对路径>
```

- 用 outline 给出的小节行号 + 文件读取工具（offset/limit）**只读相关小节**；不要整篇通读，不要一次读 10 页。
- 必读优先级：
  1. 目标格式的规范页（`wiki/templates/word-文档写作模板.md` 或 `ppt-演示文稿写作模板.md`）；
  2. 主题最相关的 `concepts/` 或 `comparisons/` 页；
  3. 我方可写产品页：`entities/ChatBI智能问数系统.md`、`entities/BI-Report可视化报表系统.md`；
  4. 涉及口径/包装：`wiki/templates/README.md` §三 + `wiki/deliverables/packaging/`；
  5. 涉及现场问题：`wiki/issues/检索入口.md`。
- 边读边记**可引用结论**：`页面路径 + 结论/数字 + 置信度标注 + 日期`。这些是提示词"依据"段的原料。

### 第 3 步：判断知识缺口（决定提示词的诚实度）

| 情况 | 写进哪里 |
|---|---|
| 知识库有依据 | "知识库依据"段：`wiki/...` + 具体结论 |
| 用户提供了 | "用户输入/约束"段，注明来源是用户 |
| 都没有 | **不得编造**：标 `【待验证】` 放进"待确认"，并在交付时建议"先摄入哪类素材" |

### 第 4 步：按蓝图写提示词

读 `references/prompt-blueprints.md`（八段式结构、三格式变体、句库、反模式）。硬性要求：

1. **知识库依据段**：逐条写 `wiki/路径` + 该页能支撑的**具体结论或数字**。禁止写"请参考知识库/相关资料"。
2. **输出规格段**：格式、母版与规范页的**绝对路径**、场景骨架、篇幅、命名规则（`YYYYMMDD-<产品>-<主题>-<版本>`）。
3. **口径与红线段**：内部/外发/公开；外发隐去 Hermes 等底层框架名、统一称"自研 Agent 引擎"；**不得改称不实归属**；**不得删除第三方引用**；数字必须带出处与日期。
4. **验收清单段**：直接取规范页自检清单（Word 10 项 / PPT 11 项），不要自己发明指标。
5. **未决问题段**：假设 + 待确认项，每项给出最省事的确认方式（"给我一句话即可"）。
6. 提示词要能**独立执行**：换个没有本次对话上下文的 AI 也能照做。

### 第 5 步：按固定结构交付

~~~markdown
## 优化点摘要（≤6 条）
- 补了什么：<例如 口径从"没说"变成"外发+脱敏规则">
- 依据了什么：<wiki 页面>
- 定了什么规格：<格式/母版/骨架/篇幅>
- 还缺什么：<待确认 1–3 条>

## 可直接复制的提示词
```text
（八段式提示词正文）
```

## 依据与置信度
- `wiki/...` — 支撑哪一句（【已验证】/【推断】/【待验证】）
- 建议先摄入：<素材类型>（如果没有依据）

## 下一步（可选）
- 说"就按这个做"→ 我按提示词生成文档（docx/pptx 会套公司母版并跑自检）
- 说"太长了/再专业点/换成 PPT"→ 我只改对应段落
~~~

### 第 6 步（仅当用户要求执行）

用户确认"就按这个做"后：
- docx / pptx：先加载 `office-docx` / `office-pptx` 技能，按提示词执行；**先写 Markdown 内容源，再套母版生成成品**，最后逐项跑自检清单并汇报未决项与口径。
- md：直接产出内容源，命名与存放遵循 KB 约定。

## 二、质量红线

1. **不虚构**：知识库没有的结论、数字、竞品事实，一律不写；不确定就标 `【待验证】` 或进待确认。
2. **不改原意**：用户的核心诉求、硬约束、指定章节必须保留；优化是"补全 + 结构化 + 加规格"，不是换题。
3. **不搬运**：提示词里引用路径与结论即可，不要把 wiki 整页贴进去（提示词长度一般 600–1500 字，PPT 类 400–900 字，用户要详细时不超过 2500 字）。
4. **口径默认从严**：对外场景默认 `外发`；拿不准时在提示词里写"口径待确认：默认外发"。
5. **数字必须有出处与日期**；转引标 `【待验证】`；竞品只写官方公开材料。
6. 中文输出；术语首次出现给全称与缩写；同一文档内术语统一。

## 三、迭代口令（用户后续调整）

| 用户说 | 你只改 |
|---|---|
| 太长 / 太啰嗦 | 压缩"背景"与"写作规范"，保留依据、规格、验收 |
| 太短 / 不够细 | 扩"输出规格"与"验收清单"，补场景骨架章节 |
| 更专业 | 补依据与验收标准、收紧口径与术语，**不加形容词** |
| 换成 PPT / 换成 Word | 只改"输出规格"与"交付"两段（套对应规范与母版） |
| 更通用 | 去掉 `wiki/` 具体路径，改为"按知识库检索结果"并保留检索指令 |
| 直接用 | 进入第 6 步执行 |
